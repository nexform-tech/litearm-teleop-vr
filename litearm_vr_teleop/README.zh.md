# litearm_vr_teleop（中文）

七轴 LiteArm + LiteGrip 夹爪的 VR 遥操，跑在 ros2_control 上。

Quest 3 手柄经与 MoveIt 栈**同一条硬件通路**驱动臂与夹爪，只有一处刻意不同：本栈跑的是
**forward 控制器**而不是轨迹控制器，并且**规划在遥操节点里做**、不在 MoveIt 里做。头显的
WebSocket 通信是 `vr_control` 里原样保留下来的那部分；规划算术是从它的 pybullet 仿真**移植
到 C++** 的。

> 代码注释与英文 `README.md` 为英文；本文件是中文文档，与英文版不一致时以英文为准。
> 快速上手见仓库根的 [`QUICKSTART.zh.md`](../docs/QUICKSTART.zh.md)。

## 一、数据流

```text
Quest 3 WebXR 页面（~72 Hz，每帧一条 JSON，ws 明文）
        │
        ▼  ws://<本机>:8765
headset_link.py            只做传输：解析、发布、计数
        │
        ▼  /vr_controller_frame（litearm_vr_teleop/msg/VrControllerFrame）
vr_teleop_node             遥操语义 + 规划 + 指令流（C++，100 Hz 定周期）
        │        │
        │        └──→ /gripper_controller/gripper_cmd（GripperCommand 动作）
        ▼
        /vr_forward_controller/commands（Float64MultiArray，7 个位置）
        │
        ▼
VrForwardController        ros2_control 控制器：同帧写 position 与 velocity
        │
        ▼
LitearmSystem / mock       <ros2_control> 硬件组件
        │
        ▼
固件守护进程 → USB CDC → 臂        （或 mock、或 pty 上的假固件）
```

## 二、为什么必须是 forward 控制器，而且必须写速度

官方的 `forward_command_controller/ForwardCommandController` 每个关节写一条接口，而在本机
臂上那样做的结果是**「臂收下指令但一步不动」**：固件把指令帧里的 velocity 读作位置参考的
斜坡上限；只认领 `position` 的控制器会把 velocity 接口留在硬件初始化时的值上，也就是 0，
于是参考被冻结。**没有任何地方会报错。**

所以 `VrForwardController`：

- 派生自 `forward_command_controller::ForwardControllersBase` —— 它确实是一个 forward
  控制器：指令流进、硬件接口出，没有轨迹、没有目标、没有「完成判据」；
- 覆盖 `update()`，把两条接口一起写，并且**速度由指令流自身差分得出**（`(q_cmd − q_cmd_prev)/dt`），
  再用 `max_velocity` 钳位。

另外两处覆盖，理由都写在覆盖点旁边：

- **`command_interface_configuration()`**：本机 ros2_control（**2.54.2**）的基类返回的是**裸
  接口名** `["position","velocity"]`，而不是 `关节/接口`。控制器管理器不把它当空配置，而
  是**整个管理器进程 abort**：
  `Character '/', was not find in the interface name 'position'`。自己拼名即可。
- **`on_configure()`**：自己建订阅，好把每条消息的**到达时刻**记下来。陈旧判据不能只看值，
  因为「持位」本身就是一个合法的值。命令陈旧时控制器**按实测位姿 + 速度 0** 持位 —— 这是
  本机固件唯一真正的「停住」姿势。

## 三、遥操行为分布在哪

| 部件 | 文件 | 决定什么 |
|---|---|---|
| 增量映射 | `include/litearm_vr_teleop/teleop_math.hpp` | 手柄位姿差 → 末端目标位姿：帧对应、滑动平均、逐轴符号 |
| 关节滤波 | 同上 | 先对**请求的速率**低通，再做每周期步长钳位 |
| 点到点轮廓 | `include/litearm_vr_teleop/joint_move.hpp` | 回起点姿态的那一次运动 |
| 规划 | `include/litearm_vr_teleop/teleop_planner.hpp` | 正运动学、雅可比、两套 IK 后端 |
| 状态机 | `src/vr_teleop_node.cpp` | grip/trigger 边沿、头显看门狗、stop 服务、什么时候发什么 |
| 传输 | `python/headset_link.py` | WebSocket、帧解析，别的什么都不做 |

这条分界线是刻意画的：**可能伤到人的部分全在 C++ 且有用例，不会伤到人的部分才在 Python。**

### 手柄的旋转怎么传到末端

`config/vr_teleop.yaml` 里的 `rotation_mode` 二选一，差别就是操作员转手时看到什么：

- **`world`（默认）** —— 末端绕**世界**里同一根轴、转同样的角度：手柄滚转，夹爪跟着滚转；手柄摆头，
  夹爪的头在房间里朝同一个方向摆。它与臂的姿态无关，也与手柄怎么握无关。
- **`tool`** —— 末端在**自己的**坐标系里逐轴照抄手柄。只有当中末端的坐标系与手柄的坐标系处在
  某一个特定关系时，它才等于上面那个动作。

默认取 `world`，原因是那个"特定关系"**属于臂的姿态而不是属于这套设备**：参考实现那组逐轴符号是
在**手腕滚转使末端自身 Y 轴竖直向下**的姿态上实测的；换成别的滚转，末端坐标系相对世界就整体滚了
那么多，`tool` 会把手部的旋转答成一个**被旋转了同样角度**的运动。而本包的遥操起点姿态，手腕滚转
与那个实测姿态差了约 95° —— 操作员一上手就能感觉到。两种模式在实测姿态上**逐位相同**，所以
`world` 在当初测量它的地方复现那次实测动作，在别处也不再漂。

帧对应关系（头显参考系是重力对齐的、但相对机器人有偏航）仍然是**实测常量**，它按安装分档，因为
它取决于操作员站在哪一侧。位于它之上的两个参数是**活的** —— 能判断符号对不对的人就是握着
手柄的那个人：

```bash
ros2 param set /vr_teleop rotation_signs "[1.0, 1.0, -1.0]"
ros2 param set /vr_teleop rotation_mode tool
```

`rotation_signs` 默认 `[1, 1, 1]`，含义是**"该模式按实测原样"**：它是叠在该模式自身基准之上的一层修正
—— `world` 的基准是"无"，`tool` 的基准是参考实现实测的 `[1, -1, -1]`。这样"在线切到 `tool`"拿到的
才是**上一版那套实测行为**，而不是一套漏掉符号的 tool 模式。修正逐轴作用在**该模式读取的那个
坐标系**里：`world` 是机器人轴、`tool` 是末端自身轴。它留给几何修不了的情况 —— 头显参考系被镜像，
或者手柄被习惯性倒着握。改完**下一帧**生效，在那之前臂保持不动。

### 抖动，以及指令流里那几个数是怎么来的

三件独立的事决定指令流顺不顺：

**逆解每个手柄帧只解一次，不是每个控制周期解一次。** 笛卡尔目标只在帧到达时变，但求解器原先每周期
都拿同一个目标重解、种子取实测关节；求解器不是确定性的（SNS 的搜索会在 7 轴零空间里随机重启），
于是同一个目标返回的解每周期都在动 —— 几百分之一弧度的关节抖动，在本机表现出的症状正是"手没动、
指令却在动"。现在帧间直接重发上一次的解（固件的看门狗要的是连续流，不是连续新目标），关节滤波在
帧间继续向它收敛 —— 一帧的步长因此变成一小段斜坡而不是台阶。mock 上实测：**手完全静止时指令逐
采样变化 0.00000 rad**（改前一个周期就跳 0.049 rad），加 0.3 mm 模拟跟踪噪声后速度请求峰值
**0.14 rad/s**（控制器上限 1.0）。

**求解种子改用上一次的解**：同目标 + 同种子 ⇒ 同答案，冗余轴不再在零空间里漂。

**控制器写出的速度 = 步长 ÷ 两次指令到达的间隔，而不是 ÷ 控制周期。** 固件把该字段当位置参考的
斜坡上限，所以诚实的值是"操作员用多久走完这一步"。本控制器跑 100 Hz、遥操节点跑不到（它每条指令都要
解逆解）：除以控制周期等于把请求放大两者之比 —— 23 Hz 下 0.02 rad 的步长本来值 0.46 rad/s，被算成
2.0 再被 1.0 的上限削平，于是**每一步都在请求满速** —— 这正是"速度曲线贴着上限"的机理。

`target_deadband_m` / `target_deadband_rad`（默认都是 0）把低于阈值的目标变化整个挡在求解之外。抬它
之前先看清代价：目标每帧都在实测位姿上重新基准，所以低于死区的增量是**被丢掉**而不是被累积；0.5 mm
的死区在 72 Hz 下等价于 3.6 cm/s 的速度门限。0 表示每个变化都送进求解。

### 跟随比例，以及唯一能改它的开关

映射是速度式、且每帧把目标重新基准到实测位姿上 —— 这正是"被拒的目标不会累积"的来源。代价是臂在一个
周期里没走到的位移会被丢掉而不是被带着走；在滞后的被控对象上（真机固件、以及 sim launch 的假固件），
末端只走出操作员位移的一个零头。mock（无滞后）上 12 cm 手部移动交付约 60%，sim launch 自己的文档
写的是约四分之一。操作员的感受就是"手要挥很大幅度，臂才动一点"。

`reference_pose: commanded` 改成累加在"上一次指令位姿"上，臂的欠账会被带着走、等它追得上时交付；
`max_target_lead_m` / `max_target_lead_rad` 限制目标允许超前多少。它**默认关**：恢复跟随比例是
"真机上量过之后再定"的决定，因为它把"臂落后并且忘掉"换成了"臂事后追上来"，哪个更糟只有真机能回答。

### 控制环并没有跑在配置的频率上

`control_rate_hz` 写的是 100，而本机跟随过程中实际约 **23 Hz**：每周期要做正运动学 + 一次逆解 + 滤波，
SNS 插件塞不进 10 ms。这个频率可以从指令流直接量（节点每周期发一次），握着握把时
`ros2 topic hz /vr_forward_controller/commands` 即可。

于是**所有按 `dt` 标定的东西都按错的数在算**：关节滤波的 `alpha = dt/(dt + low_pass_tau)` 变成 0.68
而不是 0.33（每次都立刻放行三分之二），每周期步长上限变成 0.086 rad 而不是 0.02。两个后果值得知道：
平滑比常量写明的弱得多；手柄帧到达比消费快（72 对 23），平均窗口在墙钟上覆盖约 0.4 s 而不是 0.14 s
—— 这也是上面那个跟随缺口的来源之一。

诚实的修法按顺序是：把求解挪出控制环（或换更便宜的后端），或者把 `control_rate_hz` 降到节点真能跑到的
数字、并按那个数字重新标定所有 `dt` 相关量。**不该做的是**：配置写着 100 Hz，而系数是按 43 ms 算的。

### 遥操语义

- **按下 grip**：先以**各轴同速**回到遥操起点姿态（行程小的轴先到先停 —— 这是 SDK 的
  `movej` 语义，不是 `movej_sync`），到位后才开始跟随。
- **松开 grip**：持位（写实测位置 + 速度 0）。下一次按 grip 会**重新回起点**。
- **扣/松扳机**：夹爪闭合/张开。带 0.05 s 消抖 + 0.5 s 最小闭合窗口（防止「刚闭合还没夹住
  就松开」）。
- **头显看门狗**：`headset_timeout_s`（默认 0.5 s）收不到帧就持位，并且**下次按 grip 重新
  锚定** —— 头显重连后的位姿与断连前不连续，不能当成连续的。
- **`~/stop` / `~/start`**：外部停车 / 恢复。stop 是幂等的、随时可用；恢复必须显式调用。

### 两套 IK 后端（可配置切换）

| 后端 | 说明 |
|---|---|
| `plugin`（默认） | 用 pluginlib 按**类名**加载 MoveIt 配置里指定的求解器（本机 = `sns_ik_kinematics_plugin::SnsIkKinematicsPlugin`），求解器自己的调参（`solver_type` / `loop_period` / `eps` / `timeout`）从节点参数读 —— 这正是「复用 moveitconfig」最字面的做法。代价：单次求解的时延不归本节点管（配置给的预算是 0.2 s）。 |
| `dls` | 自研阻尼最小二乘，架在 MoveIt core 已提供的正运动学与雅可比之上：以实测关节角为种子、用阻尼项代替对奇异雅可比求逆、零空间往种子拉（7 轴 6 自由度，冗余方向需要有定义）。时延可预期。 |

两者都用**同一个验收方式**：拿解回去跑一遍正运动学，比对位置/姿态残差（3 mm / 0.05 rad，
移植自参考实现）。**不信求解器自己报的成功标志**，也不信求解器自己报的失败 —— 解超差就当作
无解，此时**持位**而不是把带残差的方向发给操作员。

## 四、两个 launch

```bash
ros2 launch litearm_vr_teleop teleop_virtual.launch.xml   # mock 硬件
ros2 launch litearm_vr_teleop teleop_sim.launch.xml       # 假固件，真协议
```

两者起同样的控制器和同样的节点，差别只在最后那一厘米，而这一厘米决定了这次运行**能告诉你
什么**。

**virtual** 用 `mock_components/GenericSystem` 顶替硬件：没有固件、没有守护进程、没有共享
内存、没有协议，被控对象「即时到位」。用它便宜地看整条路跑起来，以及校验**算术**：轴方向、
能不能回到起点姿态、夹爪、松手会不会漂。本机实测：回到起点姿态的最大误差 **0.0003 rad**；
手柄右移 12 cm → 末端 base +x 走 **0.1249 m**（多出的 4% 是设计内的平滑拖尾）。

**sim** 起真的固件守护进程但用 `--dry-run`：真协议、真帧、真上报率，固件换成 pty 上的假
固件。用它校验**只有真链路才存在的行为**：固件是否接受这条指令流、指令流是否连续（固件有
100 ms 看门狗）、两条命令接口是否都写了。**它就是「只写位置的控制器」与本控制器的分界线**，
因为假固件会像真固件一样在 velocity 为 0 时冻结参考。

它自己的文档警告不要从这里读动力学，这个警告是认真的：假固件是一阶运动学模型，在这里量到的
跟随误差或跟随比例说明不了任何事。本机实测：臂**确实会动、方向也对**，但末端只走出指令位移
的约四分之一 —— 这是一阶滞后被「目标每帧按实测位姿重新基准」的速度式映射放大的结果，**不是
指令通道的问题**（同一份代码在 mock 上是 1.04 倍）。

两个 launch 都**碰不到真机**：dry run 是硬编码而不是可传参数，共享内存段名也单独取
（`/litearm_vr_hw`，不是臂栈的 `/litearm_hw`），所以本栈不可能接到一个正在跑的臂栈的段上。
真机 launch = 把 `teleop_sim.launch.xml` 复制一份、从守护进程参数里去掉 `--dry-run`、把共享
内存段名改回去 —— 但用之前先看第七节那四条。另外：**故意不起 `move_group`**，因为规划在
`vr_teleop_node` 里，再起一个规划节点就是第二个没人用的规划入口（它还会和本控制器抢
`joint1..7` 的接口）。

## 五、配置

**`config/vr_controllers.yaml`** —— 控制器声明与参数。注意**一条命令接口同时只能被一个激活的
控制器认领**，所以本文件是**替换**臂栈那份、不是叠加：轨迹控制器认领导同几条接口，两者不能
同时在跑。

这个文件里还有一条值得单独读的注释：`/joint_states` 的**数组顺序不是 `joint1..7`，而且每次
重启都可能变**（本机实测两次同样的 launch 得到同一个集合、不同的顺序，夹爪在两端各出现一次）。
给广播器配 `joints`/`interfaces` 只能筛「发哪些」，管不了「按什么顺序发」。**所以一律按名字取**
—— 按 `position[i]` 取值的消费者会拿到一组「看起来很像数据」的乱序关节角，而且两次运行还不
一样。

**`config/vr_teleop.yaml`** —— 两个节点的参数。**两个节点都不决定臂能多快**：那属于控制器与
固件。所以本文件里写错也抬不高硬件的速度上限。

逆运动学求解器及其四个调参、以及遥操起点姿态，在两个地方各存一份：这里，和
`litearm_vr_moveit_config`（MoveIt 从那里读、SRDF 也在那里给起点姿态命名）。重复而不是引用
的原因：MoveIt 的 kinematics 文件顶层没有节点名，没法当参数文件喂给节点。这份重复由
`test/test_kinematics_consistency.py` 兜着 —— 两边漂开就测试失败。同一个测试文件还会检查全
包 XML 注释里没有连续两个连字符，这不是洁癖：在标题下画一条虚线很容易手滑，一画它就不再是
合法 XML，而报错指着的是一行散文而不是那两个字符。

## 六、launch 会替你决定的一个名字（臂描述包）

「虚拟」launch 需要**不含 ros2_control 块**的臂描述，描述包是 `litearm_description`，xacro 又没法
用变量拼 `$(find ...)`。所以 `litearm_vr_moveit_config` 在**构建期**按 ament index 把名字探出来
记到 `config/arm_description_package.txt`，launch 读它、再作为路径传给 xacro。启动横幅第二行会
打印实际用的是哪个 —— 名字对不上时第一眼就能看见：

```text
  mock hardware: true
  arm description: litearm_description
```

探测不止看名字，还**真的读那份 URDF**，确认它声明了 `joint1` 与 `ee_link`：本包整套（mock 硬件
块、夹爪挂载、配置里的关节名）都按这套命名写。若装的是那一臂**已被取代的 CAD 导出**
（关节 `Joint1..Joint7`、link `Link1..Link7`、法兰 `ee_frame_link`），构建期就会带着原因停下，
而不是让你看到一份 urdfdom 拒绝的 URDF（`parent link [ee_link] of joint [gripper_mount_joint] not found`）。

要指定别的名字：`arm_description_package:=<包名>`。细节见
`litearm_vr_moveit_config/README.zh.md`。

## 七、哪些解释器跑 Python 节点

本机系统 `python3` **没有** `websockets`，ROS 安装也不提供。`headset_link.py` 启动时先查，
缺了就 `execve` 进 `LITEARM_VR_PYTHON` 指定的解释器（默认
`$HOME/venvs/metavr-arm/bin/python`）。这个自举是**原地**的（保持 PID），所以 launch 的进程
管理与 SIGINT 投递都不变；已经有 `websockets` 时整段跳过（`LITEARM_VR_PYTHON` 由 launch 参数
`headset_python` 设置）。

## 八、真机之前要处理的事

按会被咬到的顺序：

1. **夹爪不会动。** 它的控制器在 `litegrip_max_feedback_velocity_rad_s` 还是 fail-closed 默认值
   时**拒绝发任何运动帧**。真机上这个值必须实际标定（让它跑一遍真实工况、取峰值反馈速度、
   再加余量）。两个 launch 传的是一个只对仿真被控对象成立的推导值，注释里写明了。
2. **跟随比例。** 「目标每帧按实测末端位姿重新基准」的速度式映射，在任何滞后的被控对象上都会
   少走。如果操作员觉得臂慢，改法是**把目标累加在上一次「指令」位姿上**而不是实测位姿上，
   并为「臂跟不上」的情况加个 windup 保护。**这是一个决定，不是 bug 修复**，应该在真机上量过
   之后再定，而不是先改。
3. **速度上限。** 控制器的 `max_velocity` 是 1.0 rad/s，远低于固件自己的上限。它是护栏，不是
   整定旋钮。
4. **起点姿态。** 它就是 SRDF 里的 `grasp_ready`，臂在跟随任何东西之前会先走过去。要从臂**实际
   可能起步的那些位姿**确认它不碰东西，不能只看演示位姿。


C++ 用例（对理想被控对象）：手柄不动 → 臂不动；手柄匀速 → 同速跟随；突然停手 → 平滑拖尾有界；

## 十、本包不包含

- **真机 launch**（见第七节，刻意不做）。
- **`move_group`**，以及随之而来的任何 MoveIt 规划：规划就是本节点。
- 对 `litearm_ros2_control`、`litegrip_ros2_control`、臂的 MoveIt 配置的**任何修改**：本包依赖
  它们，替换任何一个都没有。
- **双臂**。映射按单臂正装配置；帧消息本来就带了每只手的 `side`，所以接第二条臂需要的是第二个
  控制器实例与 `vr_control` 实测的左右轴配置，不是一条新消息。
